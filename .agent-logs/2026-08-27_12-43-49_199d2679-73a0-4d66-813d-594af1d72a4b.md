**Three bugs I found and fixed, all of which would have shipped:**

**Message ordering was wrong.** I dispatched each send with `void deliver(...)`, so ten quick messages became ten concurrent transactions racing for the row lock. Sequences came out unique and monotonic but scrambled: `sent 0,1,2,3…` arrived as `2,0,1,6,8,9,7,3,5,4`. A row lock serialises access, it does not preserve arrival order. Each connection now owns a promise chain, so a person's own messages stay in the order they typed them.

**Replay could silently drop a message.** A message published while a connection was still loading history would be sent first, advance the cursor past the replay, and cause the replay to be skipped as stale. Live messages now buffer during `loading` and drain after `ready`.

**`app.close()` hung forever.** WebSocket connections never drain, so Fastify waits indefinitely. It looked like a hanging test suite. Sockets are now tracked and closed on shutdown with a proper close code, plus `forceCloseConnections: true`. That's a real graceful-shutdown requirement.

**On the design decisions you asked me not to shortcut:**

- **Sequence under a row lock, not `bigserial`.** A global serial would have been simpler and wrong: concurrent inserts commit out of order, so a client can observe seq 5 before seq 4 exists, resume from 5, and lose a message permanently.
- **Auth resolved before the upgrade.** Verified by writing a raw HTTP upgrade by hand and asserting the bytes: `HTTP/1.1 401 Unauthorized`, never a 101. I had to do it that way because Bun prints `ws.WebSocket 'unexpected-response' event is not implemented in bun`, so the client can't observe rejections. The raw assertion is stronger anyway.
- **Signed tickets for the browser.** A browser can't set a `Cookie` header on a WebSocket, and Next doesn't reliably proxy upgrades. The client fetches an HMAC-signed ticket over the existing same-origin proxy, bound to one user and one conversation, valid 30 seconds, verified with `timingSafeEqual`. Tests cover a tampered signature and a ticket used on a different conversation. Cookie auth still works, so nothing depends on tickets.

**Also in:** heartbeat with liveness timeout, backpressure disconnect at 1MB buffered, per-connection rate limiting, idempotent sends (a retry returns the original sequence), and a `Broker` interface so Redis is a swap rather than a rewrite.

**Not done:** the SSE status stream, which is the other half of Phase 3.
